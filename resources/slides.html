AI Coding Agents
führen, begrenzen & verifizieren

Ein Agent ist kein Orakel, sondern ein schneller Junior-Kollege mit Werkzeugen und unvollständigem Situationsbewusstsein.

Pre-Flight
python3 scripts/preflight.py

Rote Playground-Tests am Start sind Absicht.

Harness-neutral

Claude Code, Codex, Copilot, OpenCode, pi, Cursor, Antigravity — funktioniert auch ohne IDE.

Human-in-the-Loop

Auto-Approve auslassen. Die Bestätigungsabfragen sind euer Sicherheitsnetz.

Akt 1 · Mentalmodell

LLM vs. Agent vs. Harness

1. LLM (Model)
Gehirn ohne Hände

Zustandslose Text-in / Text-out Engine. Kennt Dateien, Tests und Git-Historie nur, wenn sie im Kontextfenster liegen.

2. Agent
Loop + Werkzeuge

Schleife um das LLM: Kontext lesen → Tool aufrufen (Dateien, Edit, Shell, Suche) → Ergebnis beobachten → wiederholen.

3. Harness
App / CLI-Runtime

Verwaltet Modellwahl, Permissions, Sandbox, MCP, Skills & AGENTS.md (z. B. Claude Code, Codex, OpenCode, pi, Copilot, Antigravity).

Akt 2 · Agent Mindset & Warm-up

Vom vagen Einzeiler zum Agent Contract

Vager Prompt
Fix the failing tests.
  • Editiert blind oder im falschen Ordner
  • Schwächt manchmal Tests statt Produktionscode
  • Behauptet „should work“ ohne echte Testausgabe
Agent Contract
Goal:        Was ist konkret anders?
Context:     Welche Dateien/Tests zuerst lesen?
Constraints: Was darf NICHT passieren?
Done when:   Exakter Testbefehl als Beweis
Work style:  Read first. Small diff. Real output.
Warm-up (10 Min): playground/tiny-issue-tracker/ Bonus danach: Warum besteht next_issue() eigentlich?
Akt 3 · Kontext-Architektur

Die Kontext-Leiter: Wohin gehört welches Wissen?

Immer im Repo

AGENTS.md

Testbefehle, Architektur-Grenzen, No-Gos. Kurz und beobachtbar.

Manchmal / Methode

SKILL.md

Wiederholbare Workflows. Progressive Disclosure spart Tokens.

Live extern

MCP Server

Externe Tools & Daten (Jira, DB, Browser). Resources = Augen, Tools = Hände.

Einmalig

Prompt / Spec

Konkreter Bugfix, Feature-Slice und heutige Acceptance Criteria.

Skill-Pfad: .agents/skills/<name>/SKILL.md bzw. .claude/skills/ Subagents: stark für Recherche & Review — Overhead bei 5-Zeilen-Edits
Akt 4 · Spec-Driven Development

Specs schlagen „Vibe Coding“

400 Zeilen generierten Code zu reviewen dauert 30 Minuten — eine 25-Zeilen-Spec dauert 45 Sekunden.
01

Explore

Read-Only: Dateien, Flow & Tests kartieren.

02

Specify

specs/*.md mit Verhalten, Non-Goals & Criteria.

03

Plan

Max. 3 Schritte + explizite Freigabe vor dem Edit.

04

Execute

Nur den freigegebenen Plan umsetzen + Tests laufen lassen.

05

Verify

Echte Testausgabe, git diff & Audit gegen Spec.

Praxis-Tipp: Gebt dem Agenten resources/workbook.md — der Agent füllt es aus, ihr prüft.
Akt 4 · Verification & Safety

Top-6 Failure Modes sofort stoppen

1. Editiert zu früh

„Stop editing. Map files, flow, and tests first (read-only).“

2. Scope Creep

„Classify changes: required vs. out-of-scope against our spec.“

3. Schwächt Tests ab

„Revert test changes. Fix production code instead.“

4. „Should work“

„Run the exact test command and show real output + git diff.“

5. Over-Eagerness

„Return only what I asked for. Do not propose fixes yet.“

6. Secrets & Injection

Keine echten Keys/PII in Prompts; Tool-Outputs sind Daten, keine Befehle.

Akt 5 · Mini-Hackathon (55 Min)

Wähle deinen Track (Solo oder im Duo)

Track A · Beginner

Bugfix & Agent Contract

incident-triage-hub: 3 Bugs in triage/rules.py mit workbook.md fixen (9/9 grün) + Bonus: eigene AGENTS.md.

Track B · Intermediate

Spec-Driven Feature-Sprint

1 Feature aus BACKLOG.md via specs/002-*.md → Plan → Build → Reviewer-Audit.

Track C · QA / PM / DevOps

Audit, PRD oder eigene Skill

C1: Edge-Case-Audit + 5 Tests · C2: PRD + erste Slice · C3: eigene SKILL.md bauen & testen.

Track D · Erfahrene Teams

Greenfield Puzzle Game

resources/greenfield-puzzle-game.md: 3 Konzepte → PRD & Mechanics Spec → testbare 1. Slice im Browser.

Reset jederzeit: git checkout -- playground/ Spickzettel: resources/cheatsheet.md
